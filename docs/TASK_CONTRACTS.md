# Открытые контракты задач

Предметные требования контрактов берутся из методички и не должны добавлять
неуказанные размеры, стили, форматы входа или правила разрешения неоднозначных
результатов. Наборы входных и ожидаемых значений хранятся отдельно для каждой
задачи в `docker-grader/contracts/labN/`.

Именованные ESM-экспорты и `data-testid` — технический интерфейс подключения к
grader. Они не задают дизайн, алгоритм или архитектуру решения.

## Общие правила lab2 и lab3

- Решение находится в `solution.js` или `solution.ts`.
- Файл является ES module и имеет именованный export из таблицы.
- Невалидные типы и значения вне описанного диапазона не проверяются.
- Изменение исходных массивов не проверяется, если это явно не оговорено в
  задании.
- Порядок результата проверяется только там, где он следует из задания или
  приведённого примера.

## UI-лабораторные

Для `lab1`, `lab4` и `lab5` общий контракт проверяет валидный HTML/CSS,
загрузку страницы и локальных ресурсов, видимость `body`, отсутствие ошибок
консоли и горизонтального overflow. Требования к конкретным элементам и их
оформлению берутся только из контракта задачи.
Для всех 40 вариантов `lab1` дополнительно проверяются объективные требования
конкретной задачи: структура DOM, размеры и computed styles, псевдоэлементы,
hover-состояния, позиционирование и адаптивные layouts. Повторяющиеся задачи
используют один контракт. Для всех вариантов `lab5` дополнительно проверяется
публичный DOM-контракт и ключевой пользовательский сценарий задачи.

В `lab4` модель должна находиться в отдельном `model.js` или `model.ts`;
дополнительные компоненты и модули разрешены. `Lab5` выполняется на React с
JavaScript или TypeScript. Для локальной разработки можно использовать Vite
или Webpack; grader не исполняет студенческие build-скрипты, а собирает
приложение доверенным esbuild.

## Lab4

`model.js|ts` является ES module. Класс варианта и пять функций из пункта 4.2
экспортируются именованно. Названия экспортов зафиксированы в
`docker-grader/tasks/lab4.json`. Классы называются в PascalCase, даже если в
методичке имя написано со строчной буквы.

Model validation проверяет:

- конструктор, исходные поля и обязательные getter;
- добавление и удаление вложенной сущности;
- пересчёт среднего балла или суммы там, где это требует вариант;
- наличие и поведение пяти именованных функций пункта 4.2 на непустой коллекции;
- наличие возвращаемого значения. Синхронность функций и изменение входной
  коллекции не ограничиваются, если этого нет в тексте задания.

Входные данные и ожидаемые признаки результатов для функций находятся в
`docker-grader/contracts/lab4/queries.json`.

Для браузерной проверки используется минимальный публичный DOM-контракт:

| Элемент           | Обязательный селектор                           |
| ----------------- | ----------------------------------------------- |
| Список сущностей  | `[data-testid="entity-list"]`                   |
| Форма добавления  | `form[data-testid="entity-form"]`               |
| Карточка сущности | `[data-testid="entity-card"]`                   |
| Удаление карточки | `[data-testid="delete-entity"]` внутри карточки |

Поля основной формы имеют атрибут `name`, совпадающий с именем поля модели.
Конкретные поля каждого варианта перечислены в `ui.fields` файла
`docker-grader/tasks/lab4.json`.

Browser validation очищает localStorage, добавляет уникальную сущность через
форму и проверяет, что:

- обработчик использует `setTimeout`, а карточка появляется асинхронно;
- интерфейс обновляется без перезагрузки;
- добавленная сущность записана в localStorage и восстанавливается после reload;
- удаление также асинхронно обновляет DOM и localStorage.

## Lab5

В корне `lab5` должен находиться `package.json`, который объявляет `react`,
`react-dom`, один из сборщиков `vite`/`webpack` и script `build`. Manifest нужен
для локальной разработки и проверки структуры, но CI не устанавливает его
зависимости и не исполняет scripts.

HTML располагается в `index.html` либо `public/index.html`. React entry может
быть явно подключён локальным `script src` или находиться в одном из стандартных
мест: `main.*`, `src/main.*`, `src/index.*`, где расширение — `.js`, `.jsx`,
`.ts` или `.tsx`. В проекте должен быть хотя бы один CSS-файл. Такая структура
совместима с Vite и Webpack, но не позволяет конфигурации сборщика исполнять
недоверенный Node-код внутри grader.

Соответствие всех 40 вариантов задачам хранится в
`docker-grader/tasks/variants.json`, а 25 уникальных задач — в
`docker-grader/tasks/lab5.json`. Варианты 26–40 повторно используют контракты
соответствующих задач и не дублируют код проверки.

Корневой элемент приложения должен иметь `data-testid="app"`. Остальные
обязательные `data-testid` конкретной задачи перечислены в открытом файле
`docker-grader/contracts/lab5/scenarios.json`. Атрибуты не задают дизайн и не
влияют на работу приложения; они создают стабильную границу между произвольной
компонентной архитектурой студента и grader.

Для каждой задачи checker сначала проверяет наличие и видимость обязательных
элементов, затем выполняет заявленный сценарий в Chromium. Декларативный
сценарий может:

- заполнить input или select;
- кликнуть элемент, нажать клавишу или выполнить drag-and-drop;
- проверить изменение текста, атрибута, количества элементов или изображения;
- проверить появление элемента и изменение localStorage.

Так проверяются ключевые требования вариантов: сортировка и пагинация книг,
слайдер, рейтинг, дерево, таймер, CRUD-приложения, формы, игры, модальное окно,
аккордеон, темы, корзина и избранное. Это не визуальный эталон и не скрытая
реализация: входные значения, селекторы, действия и ожидаемые свойства полностью
видны студенту в `scenarios.json`.

## Связь с отчётом прогресса

Progress report не запускает описанные здесь функциональные и браузерные
контракты повторно. Он сканирует основную ветку курса и считает лабораторную
принятой по наличию обязательной структуры, предполагая, что преподаватель
merge-ит только успешно проверенные PR. Отсутствующий каталог отображается как
несданная работа (`—`), а существующий каталог с неполной структурой — как
предупреждение. Запуск по локальному или удалённому репозиторию описан в
[руководстве по эксплуатации](USAGE.md#13-progress-report).
